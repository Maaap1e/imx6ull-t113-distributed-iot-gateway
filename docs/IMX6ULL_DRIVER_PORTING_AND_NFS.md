# i.MX6ULL 传感器驱动适配与 NFS 联调说明

## 1. 文档目的与贡献边界

本文说明 AP3216C 和 ICM20608 在 i.MX6ULL 平台上的板级适配、用户态接入及 NFS 联调过程，用于补充主项目中 Linux 驱动与 BSP 相关工作的技术背景。

两类传感器驱动均以 i.MX6ULL 官方 BSP 和开发板例程为基线：

- AP3216C 通过 I2C 接入，用于采集环境光、红外和接近数据；
- ICM20608 通过 SPI 接入，用于采集三轴陀螺仪、三轴加速度和芯片温度。

本项目完成的工作集中在板级设备树适配、例程驱动修改、寄存器数据通路调整、字符设备接口联调及用户态集成，不包含对 Linux I2C/SPI 核心框架的重新实现。因此，对外描述该部分工作时使用“基于官方或开发板例程完成驱动适配与修改”，而不表述为“从零编写完整传感器驱动”。

完整内核和板级 BSP 未直接纳入本仓库。仓库已提供项目使用的最小驱动源码、外部模块 Makefile、共享 UAPI 和传感器 DTSI，位置为 [`linux/kernel_drivers/imx6ull_sensors`](../linux/kernel_drivers/imx6ull_sensors)。

## 2. 板端数据通路

适配后的传感器数据从字符设备进入 i.MX6ULL 网关；网关同时保留对早期 AP3216C sysfs 接口的兼容读取：

```text
AP3216C
  └─ I2C 控制器
      └─ AP3216C 驱动与设备树节点
          └─ /dev/ap3216c

ICM20608
  └─ SPI 控制器
      └─ ICM20608 驱动与设备树节点
          └─ /dev/icm20608

上述数据
  └─ linux/imx6ull_gateway/sensors.c
      └─ 网关状态快照
          ├─ 自定义 TCP → T113/LVGL
          └─ MQTT → Windows Qt 上位机
```

AP3216C 的网关读取同时兼容旧 sysfs 属性和 `/dev/ap3216c`；当前公开驱动的标准出口是字符设备。ICM20608 通过 `/dev/icm20608` 返回原始数据，网关再换算为角速度、加速度和温度。

设备路径集中定义在 [`config/imx6ull.conf`](../config/imx6ull.conf)，具体读取与单位换算位于 [`linux/imx6ull_gateway/sensors.c`](../linux/imx6ull_gateway/sensors.c)。

## 3. 已完成的适配工作

### 3.1 设备树与板级配置

设备树修改围绕开发板实际原理图完成，主要涉及：

- 启用 AP3216C 所在的 I2C 控制器和 ICM20608 所在的 SPI 控制器；
- 使设备节点的 `compatible` 与驱动匹配表保持一致；
- 按硬件连接配置 I2C 地址、SPI 片选和节点状态；
- 配置 SPI 工作参数以及相关 pinctrl 引脚复用；
- 确认内核启动后设备能够被枚举并进入驱动 `probe` 流程。

这部分工作的核心不是增加新的总线协议，而是把通用例程与当前开发板的控制器、引脚和设备连接对应起来，使驱动能够在实际硬件上正确绑定。

### 3.2 驱动与字符设备数据通路

在例程驱动基础上完成了寄存器访问和用户态数据通路的调整，涉及：

- 传感器初始化及芯片 ID/状态寄存器验证；
- I2C、SPI 寄存器读写封装；
- 字符设备注册以及 `open`、`read`、`release` 等接口联调；
- 原始寄存器数据到用户缓冲区的数据组织；
- 设备未就绪、总线传输失败和用户缓冲区异常等错误处理；
- `remove` 及初始化失败路径中的资源释放。

整理进仓库的版本还完成了三项关键修改：

- ICM20608 连续寄存器读取改用 `spi_write_then_read()`，修复旧实现从 1 字节发送缓冲区执行多字节传输的问题；
- 两个驱动均返回总线和 `copy_to_user()` 错误，并使用互斥锁保护同一设备的寄存器访问；
- [`sensor_uapi.h`](../linux/kernel_drivers/imx6ull_sensors/sensor_uapi.h) 统一驱动、网关和诊断程序的数据布局，CI 通过 `sensor_uapi_test` 检查结构体大小与字段偏移。

网关应用兼容了开发板例程中 `read()` 成功后返回 `0` 的实现，同时也接受更常见的“返回实际读取字节数”语义。该兼容处理使用户态程序不依赖单一例程的返回值约定。

### 3.3 用户态集成与故障隔离

驱动数据可先用 `sensor_smoke_test` 连续读取，确认原始读数后再启动完整网关。网关为每类传感器维护独立的有效标志：

- `ap3216c_ok` 表示 AP3216C 本轮读取有效；
- `icm20608_ok` 表示 ICM20608 本轮读取有效；
- STM32/CAN 状态通过独立状态文件汇入同一快照。

单个传感器读取失败时，网关仍会继续维护 CAN 状态、TCP 重连和其余数据发送，并在输出中显式标记异常设备。这样可以避免一个 I2C 或 SPI 外设故障导致整个边缘网关退出。

## 4. NFS 联调方式

驱动和用户态程序在 Ubuntu 虚拟机中使用 i.MX6ULL 交叉工具链构建。开发阶段通过 NFS 将构建目录共享给开发板，使新生成的内核模块和测试程序无需反复使用串口、U 盘或 SCP 复制。

实际联调链路如下：

```text
Ubuntu 虚拟机修改源码
  → 交叉编译驱动、设备树或测试程序
  → 构建产物写入 NFS 共享目录
  → i.MX6ULL 挂载共享目录
  → 加载新模块或运行测试程序
  → 结合 dmesg、/dev 节点和实际读数验证
```

下面给出与该流程等价的参考命令。IP 地址、导出路径、模块名和程序名需要按实际开发环境替换：

```sh
# Ubuntu：确认已导出的 NFS 目录
sudo exportfs -v

# i.MX6ULL：挂载 Ubuntu 构建产物目录
mkdir -p /mnt/nfs
mount -t nfs -o nolock,vers=3 \
    <VM_IP>:/path/to/imx6ull-build-output /mnt/nfs

# 确认共享目录可访问
ls -lh /mnt/nfs
```

当驱动以模块方式构建时，可直接从 NFS 目录替换并验证：

```sh
rmmod <old_module> 2>/dev/null || true
insmod /mnt/nfs/<new_module>.ko
dmesg | tail -n 50
ls -l /dev/<device>
```

用户态测试程序同样可直接从共享目录执行：

```sh
chmod +x /mnt/nfs/sensor_smoke_test
/mnt/nfs/sensor_smoke_test -n 10 -d 500
```

NFS 在这里承担的是开发期快速迭代通道，不属于产品运行依赖。正式部署使用已构建的内核、DTB 和版本化应用安装包，即使 Ubuntu 虚拟机离线，开发板仍可独立启动和运行。

## 5. 验证方法与结果

本项目采用由底向上的方式验证驱动适配结果：

1. **设备树和总线绑定**：通过启动日志确认当前 DTB 生效，并检查设备进入对应驱动的 `probe` 流程。
2. **驱动初始化**：通过 `dmesg` 确认芯片 ID、资源申请和字符设备注册结果。
3. **设备接口**：确认 `/dev/ap3216c` 和 `/dev/icm20608` 存在且可读。
4. **最小用户态测试**：直接读取原始数据，排除网络、UI 和多线程逻辑对判断的干扰。
5. **网关集成测试**：由 `sensors.c` 汇总 AP3216C、ICM20608 和 STM32/CAN 状态，检查生成的 JSON 与运行日志。
6. **系统级验证**：通过 T113/LVGL 和 Windows Qt 上位机观察实际遥测，确认本地 TCP 与 MQTT 两条链路均能接收传感器数据。

实板运行中已经观察到 AP3216C 和 ICM20608 状态为正常，ICM20608 可持续输出三轴角速度、三轴加速度和温度，AP3216C 可持续输出 ALS、IR 和 PS 数据。项目的 24 小时三节点稳定性验收以及 MQTT/Qt 增量验收也保留了传感器在线状态和实际读数：

- [v1.0.0 实板验收结果](acceptance/v1.0.0/RESULT.md)
- [v1.1.0-rc.1 MQTT/Qt 增量验收结果](acceptance/v1.1.0-rc.1/RESULT.md)

## 6. 调试定位方法

本项目形成的排查顺序是“先确认绑定，再验证数据，最后检查系统集成”：

| 层级 | 主要观察点 | 目的 |
|---|---|---|
| 设备树 | 当前 DTB、`status`、`compatible`、地址/片选、pinctrl | 确认硬件描述与实际连接一致 |
| 总线 | I2C/SPI 控制器状态、设备枚举、传输错误 | 判断问题是否发生在控制器或物理通信层 |
| 驱动 | `probe`、芯片 ID、资源申请、注册与释放日志 | 确认驱动生命周期完整 |
| 设备接口 | sysfs 属性、`/dev` 节点、权限和返回长度 | 确认内核到用户态的数据出口 |
| 最小应用 | 原始读数及连续读取结果 | 将驱动问题与业务程序问题分离 |
| 网关集成 | 有效标志、JSON 状态、TCP/MQTT 日志 | 验证异常隔离和完整数据链路 |

这种分层方式避免在驱动尚未完成匹配时直接调试 `read()`，也避免把 UI 不刷新或网络断线误判为传感器驱动故障。
